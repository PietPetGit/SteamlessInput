# 04 — UI & visual consistency

**Gate:** the project has a visual interface whose styling you control. Skip for
CLIs, headless services, and apps whose UI is entirely native/platform-drawn.

This is the consistency pass: one scale, one icon set, one set of rules. Most
findings here are P3 — but a UI with fourteen font sizes and three icon styles
reads as unfinished no matter how good the code is.

---

## A. Typography

- **Establish a modular type scale.** Audit every font-size in use and
  consolidate to one scale derived from a consistent ratio (e.g. 1.25 major
  third) anchored to a ~16px body size. Define named tiers — display, h1–h4,
  body-large, body, small, caption — and map each piece of text to the tier that
  matches its *role*. Refactor components to use the tiers instead of one-off
  sizes. Report the scale and how many distinct sizes were eliminated.
- **Fluid headings.** Use CSS `clamp()` so large text interpolates smoothly
  between a mobile minimum and desktop maximum instead of jumping at
  breakpoints, with bounds that never get uncomfortably small or large. Apply it
  where size difference matters — headings and display text — and keep body text
  at a stable, readable size. Report which styles became fluid and the min/max
  values chosen.
- **Line length and leading.** Body copy stays in a readable measure (~60–80
  characters) with line-height proportional to size — tighter for display,
  looser for body.
- **One or two families, deliberately weighted.** Every weight and style in use
  is one you chose, not one that crept in.

## B. Iconography

- **Standardize on a single icon library** and one visual style — matching
  stroke weight, corner treatment, and optical weight. Report every icon
  swapped.
- **A small set of allowed sizes**, aligned to the spacing scale.
- **Optical alignment.** Icons beside text are sized relative to the adjacent
  font-size and vertically centred on the text's optical centre, not its box.
- **Accessible names** on every interactive icon; decorative icons hidden from
  assistive tech.

## C. Colour, spacing & tokens

- **Tokens, not literals.** Colours, spacing, radii, shadows, and durations come
  from named tokens. Hunt down one-off hex values and magic pixel numbers.
- **A spacing scale** (e.g. 4px base) used consistently — no arbitrary
  `margin: 13px`.
- **Both themes work** if the app has light and dark: every colour is defined in
  both, nothing is invisible or low-contrast in either, and no component
  hardcodes a background that breaks in the other theme.
- **Semantic colour** is consistent — the same hue always means the same thing
  (danger, success, warning, info) across every surface.

## D. Components & layout

- **Container queries** for components whose layout should depend on the space
  they are given rather than the viewport — a card that stacks in a narrow
  sidebar but lays out horizontally in a wide column. Establish the container
  context properly and define sensible internal breakpoints. Report which
  components became container-aware.
- **States are complete.** Every interactive component has hover, focus-visible,
  active, disabled, loading, and error styling — not just the default state.
- **Responsive down to the smallest supported width** with no horizontal
  scrolling of the page body; wide content (tables, code, diagrams) scrolls
  inside its own container.
- **No duplicate components** doing the same job in different styles — one
  Button, one Input, one Card, one Modal.

## E. Data visualization

**Gate:** the app renders charts.

- **Right chart for the question** the reader is actually asking.
- **Clear labels, axes, legends, and units**; no unexplained abbreviations.
- **Accessible, consistent palette** — distinguishable without relying on colour
  alone, sufficient contrast, and the same series colour across every chart.
- **Empty and loading states** handled, and responsive on mobile.
- **Helpful interactivity** — tooltips on hover *and* focus where it aids
  understanding.
- **No chart junk** — remove gradients, 3D, heavy gridlines, and decoration that
  competes with the data.
