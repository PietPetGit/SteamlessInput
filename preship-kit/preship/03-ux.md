# 03 — UX & interaction

**Gate:** the project has an interactive interface — web, desktop, mobile, or
TUI. Skip entirely for libraries and headless services.

Everything here is user-visible behaviour. Test each change in the running app
before moving to the next; a UX fix that was never seen running is not a fix.

---

## A. Feedback

- **One toast/notification system.** Replace ad-hoc `alert()`s and one-off
  banners with a single component. Distinct types (success, error, warning,
  info) with matching styling and icons; auto-dismiss on a sensible timer, with
  errors persisting longer or until dismissed; manual dismissal; clean stacking
  of multiple messages; consistent position that never covers important content.
  Pause on hover, and announce via an ARIA live region. Report where it is now
  used.
- **Every action has a visible result.** No click that appears to do nothing —
  pending state on the control, success/failure feedback, and a disabled or
  busy state that prevents double submission.
- **Progress for anything slow.** Determinate progress where the total is known,
  indeterminate otherwise, and an explanation for anything over a few seconds.

## B. Loading, empty & error states

- **Skeletons on every data-fetching screen.** One reusable Skeleton component,
  sized to match the real content so nothing shifts when data arrives (see CLS
  in `02-performance.md`). Wire it into the main list and detail views first.
- **Optimistic updates** for likes, toggles, adds, edits, and deletes: update
  the UI immediately, reconcile with the server result, and roll back visibly
  with a clear error if it fails. The happy path should feel instant and a
  failure must never leave the user misled about what was saved.
- **Empty states** say what the thing is, why it is empty, and what to do next —
  with the primary action right there. Distinguish "nothing yet" from "nothing
  matched your filter".
- **Failure states** offer a retry, keep the user's input, and never dump a raw
  exception on screen.

## C. Error & validation copy

- **Rewrite unhelpful messages.** Each message must be *specific* (what exactly
  is wrong), *constructive* (how to fix it), and *human* (friendly, not blaming).
  Replace "Invalid input" with, e.g., "Please enter a valid email address like
  name@example.com". No jargon or error codes in user-facing copy — put the
  correlation id in small print if support needs it.
- **Place the message where the user is looking** — beside the offending field,
  not only in a summary at the top.
- **Validate at the right time** — on blur or submit, not on every keystroke of
  a half-typed value; clear the error as soon as it is resolved.
- Report the worst offenders and the improved copy for each.

## D. Destructive & irreversible actions

- **Audit every destructive path** — delete, remove, overwrite, cancel,
  archive, revoke, and bulk operations — and give each appropriate friction so
  it cannot be triggered accidentally.
- **Confirmation dialogs** state the consequence and name the specific item
  ("Delete project *Northwind*? This removes 24 files and cannot be undone"),
  with the confirm button labelled by the action ("Delete project") rather than
  "OK", and styled distinctly as destructive.
- **Prefer undo over confirmation** where it is feasible — a toast with Undo
  beats a modal for reversible actions. Reserve modals for the genuinely
  irreversible.
- **No destructive action as the default focus** and never adjacent to a common
  safe action without separation.
- Report which actions were protected and how.

## E. Navigation & orientation

- **Page titles.** Every page/route has a unique, descriptive document title
  that updates on client-side navigation, following one pattern (specific page
  first, then app name) so tabs, history, and bookmarks are meaningful. Confirm
  titles announce correctly to screen readers on navigation.
- **Language attribute.** `<html lang>` is set correctly and updated for
  multilingual content.
- **Breadcrumbs** where the hierarchy is genuinely deep — generated from the
  route/content hierarchy, every level clickable except the current page,
  truncating gracefully on small screens, with semantic markup and an
  `aria-label`. Do not add them to a shallow app.
- **Page transitions.** Subtle enter/exit animation (quick fade or directional
  slide) that conveys spatial relationship without slowing navigation. Handle
  scroll position sensibly, never block interaction, never cause layout shift,
  and respect `prefers-reduced-motion`.
- **Back and refresh behave.** Browser back, deep links, and a hard refresh all
  land the user somewhere sane with state intact.

## F. Search

**Gate:** the app has an in-app search.

- Search-as-you-type with debounced queries; clear loading state.
- Empty/no-results state with suggestions or a way forward when nothing matches.
- Matched terms highlighted in results; results relevant and scannable.
- Recent searches, forgiving of typos where feasible.
- Prominent, easy to invoke, and fully keyboard-operable (including a shortcut
  to focus it, arrow-key result navigation, Enter to open, Esc to close).

## G. Input & accessibility baseline

- **Keyboard.** Every interactive element reachable and operable by keyboard,
  in a sensible tab order, with a visible focus indicator. Modals trap focus
  and return it on close; Esc closes.
- **Labels.** Every input has a real label; icon-only buttons have accessible
  names; images have alt text (empty alt for decorative).
- **Contrast** meets WCAG AA, and no state is signalled by colour alone.
- **Touch targets** large enough on mobile, with no hover-only affordances.
- **Reduced motion** respected for every animation added.
